## 二、严重问题（Critical）

### 🔴 C1 · 路由鉴权形同虚设（登录功能失效）
- **证据**：`src/router/index.ts:196-200` 的 `beforeEach` 守卫**只设置 `document.title` 后无条件 `next()`**，既不读取 `meta.public`、也不校验任何登录态、不重定向 `/login`。
- **佐证**：全项目 grep `isLogin|auth|token|isAuthenticated` 仅命中 CSS 设计 `token`、`tabs/theme` 的 localStorage、**Login.vue 的"记住密码"**——**没有任何全局门禁读取这些值**。
- **影响**：登录页纯属摆设，用户可直接访问 `/sales`、`/members`、`/settings` 等任意业务路由，门店数据无访问控制。这是当前最高危问题。

### 🔴 C2 · 金额全程使用 `f64` 浮点（货币计算漂移）
- **证据**：金额字段遍布 `f64`——
  - `models/product.rs:71-72` 零售价/会员价
  - `models/inventory.rs:14,113,126,144-145,159` 成本价/单价/金额
  - `models/sales.rs:144-148,167,169` 总额/折扣/实收/单价/小计
  - `models/member_balance.rs:48-122` 变动额/余额/赠送/手续费
  - `models/supplier_payment.rs:15-57` 付款额/余额/累计
  - `models/return_order.rs:45-87` 退货单价/小计/总额
- **影响**：折扣分摊、积分累加、多单位换算等浮点运算可能产生 `0.01` 级漂移，长期累积导致账目不平。零售收银场景对分精度敏感，建议改用整数「分」或 `rust_decimal` / 前端 `decimal.js`。

## 三、高风险问题（High）

### 🟠 H1 · 生产暴露破坏性命令（清空全库无门禁）
- **证据**：`src-tauri/src/lib.rs:103-104` 在**所有构建（含 release）**的 `invoke_handler` 中注册了 `seed_demo_data` 与 `clear_all_data`；后者会清空整个 `tea_manage.db`。
- **影响**：任意能触发 invoke 的路径（或调试控制台）调用 `clear_all_data` 即销毁门店全部数据，无环境隔离、无二次确认。建议：仅 `#[cfg(debug_assertions)]` 注册，或前端必经确认弹窗 + 后端二次校验。

### 🟠 H2 · 命令处理大量 `.unwrap()`（DB 失败直接 panic）
- **证据**：`commands/return_order.rs` 在 `1169–1431` 等大量位置对 rusqlite 结果 `.unwrap()`（如 `conn.execute(...).unwrap()`、`.collect::<Result<...>>().unwrap()`）。
- **影响**：本应 `return Err(...)` 的数据库异常被升级为进程 panic，导致 Tauri 应用崩溃而非向前端返回错误。应在命令边界统一用 `?` 传播 `Result`，仅在对不变量有 100% 把握处 `.expect("明确理由")`。

### 🟠 H3 · 全局 DB 互斥锁导致请求串行化
- **证据**：`src-tauri/src/db/mod.rs:14-52`，`Database { conn: Mutex<Connection> }`；命令 `get_conn()` 后**持锁贯穿整个命令体**（含全部 DB 操作与可能的阻塞 I/O）。
- **影响**：所有命令在单把进程级锁上串行执行，并发请求无并行度；且 `std::sync::MutexGuard` 跨 `.await` 持有在 Rust 中属不良实践（潜在死锁/未定义行为隐患）。单用户 POS 当前可接受，但属设计异味，建议改读写分离或短持锁 + 事务内操作。

## 四、中风险问题（Medium）

### 🟡 M1 · UI 规范系统性偏离（约定④⑤未贯彻）
- **证据**：21 个业务页使用 `text-[var(--tea-*)]` 这类 UnoCSS 任意值直接给文字上色，绕过 `<n-text :type>`（约定④）；示例：`views/suppliers/index.vue:15-16`、`ProductForm.vue`、`PurchaseForm.vue`、`dashboard/index.vue` 等。部分标题栏用裸 `<div class="flex ...">` 代替 `n-space` 语义布局。
- **影响**：主题切换/深浅色适配时文字色可能不跟随，破坏既定「深茶绿主题铁律」的一致性。属一致性问题，非功能缺陷。
- **范围量化**：`text-[var(--tea...)]` 命中 21 个 `.vue` 文件（累计 80+ 处）。

### 🟡 M2 · 超大文件，可维护性差
- 后端：`commands/sales.rs:1912` 行、`commands/return_order.rs:1707` 行、`commands/inventory.rs:1497` 行
- 前端：`views/sales/index.vue:869` 行、`views/auth/Login.vue:669` 行、`types/index.ts:621` 行（类型定义巨文件）
- 建议按业务域拆分（如 sales 拆创建/挂单/收银台子模块）。

### 🟡 M3 · `meta.public` 死配置
- **证据**：`src/router/index.ts:185` 声明 `meta: { ..., public: true }`，但守卫从未读取（见 C1）。死配置，进一步佐证鉴权缺失。

### 🟡 M4 · 登录密码以 base64 存 localStorage（弱存储）
- **证据**：`views/auth/Login.vue:193` `localStorage.setItem(STORAGE_KEY_PASSWORD, encodeBase64(password))`。
- 影响：本地桌面应用风险较低（数据在本机），但 base64 非加密，任何能读 localStorage 的脚本可还原密码。建议至少不持久化密码，或改用安全存储。

## 五、低风险 / 已澄清（Low / Clarified）

### 🟢 L1 · SQL 拼接：安全但脆弱
- **证据**：`db/queries.rs:214`、`commands/products.rs:183` 用 `format!` 插值**内部白名单列名/表名**（`where_clause`、`updates.join`），值均走 `?` 占位参数绑定，无用户输入直接拼接。**当前无注入风险**，但列名动态拼接受白名单约束时才安全，建议封装列名白名单函数。

### 🟢 L2 · `generate_product_code` 切片越界（理论风险，非真实 bug）
- **证据**：`db/queries.rs:41` `code[prefix.len()..].parse().unwrap_or(0)`。因查询已 `WHERE code LIKE 'SP日期%'`，返回的 code 必以 prefix 开头，切片安全；仅当 code 恰等于 prefix 时 `parse` 失败落 `unwrap_or(0)`，不会 panic。Agent 此前判定为"必然 panic"系夸大，此处订正。
