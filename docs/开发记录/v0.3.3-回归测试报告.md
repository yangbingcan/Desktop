## 一、测试目标与背景

### 1.1 测试目标

针对 v0.3.2 遗留的多处功能异常、IPC 链路不通畅、人工测试效率低下等问题，建立**三层完整回归测试体系**：

1. **IPC 契约层**：保证前端 invoke 调用与后端 Tauri command 的命名/参数/序列化严格一致
2. **后端逻辑层**：通过 Rust 单元测试覆盖核心命令的业务校验与数据库操作
3. **前端逻辑层**：通过 Vitest 单元测试覆盖 utils/api/stores 的纯逻辑与状态管理

### 1.2 测试策略

| 维度 | 选择 | 理由 |
|------|------|------|
| 测试体系 | 三层完整体系 | 通信层 + 后端逻辑 + 前端逻辑 全覆盖 |
| 缺陷处理 | 边测边修 | 测试发现的契约不一致立即修复 |
| 执行节奏 | 分阶段交付 | 阶段1→2→3 逐步交付可验证成果 |
| 业务逻辑保护 | 不动业务代码 | 仅修通信层契约不一致，业务逻辑保持不变 |

## 七、风险评估与后续建议

### 7.1 数据库迁移风险

**变更**：`sales_orders.pay_status` 默认值 `'pending'` → `'unpaid'`

**影响**：
- 新数据：默认为 `'unpaid'`，与前端类型一致 ✅
- 已有数据：`pay_status = 'pending'` 的记录不会被自动迁移
- **建议**：执行 `UPDATE sales_orders SET pay_status = 'unpaid' WHERE pay_status = 'pending'` 迁移历史数据
