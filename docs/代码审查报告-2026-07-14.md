# 茶易管（TeaManage）代码全面审查报告

> 审查日期：2026-07-14
> 审查对象：茶叶店管理系统 v0.6.x（Vue 3 + Tauri 2 + Rust 后端 + SQLite）
> 方法：三路并行深度审查（Rust 后端 / Vue·TS 前端 / 规格对照），关键致命结论由主代理逐行亲自复核
> 代码规模：Rust 26 文件 / 12,318 行；Vue 33 组件 / 11,579 行；TS 30 文件 / 4,256 行（约 2.8 万行源码，已排除 node_modules/target/dist）

---

## 一、稳固度总体评估

| 维度 | 评分 | 结论 |
|------|------|------|
| 后端（Rust） | **6 / 10** | 分层清晰、SQL 全部参数化、事务原子性良好、金额 `round2` 策略基本到位；但**库存逻辑存在系统性缺陷**（计件/称重字段处理不一致、采购单修改可造负库存），且生产环境保护可被绕过 |
| 前端（Vue/TS） | **4.5 / 10** | 视觉规范/主题/组件封装成熟，但**核心业务链路有多处致命缺陷**：采购入库界面完全不可用、取单丢失会员余额、打印回退路径 XSS、采购详情空白页 |
| 功能覆盖 | **6 / 10** | 进销存+收银+会员+打印事务闭环基本可用；但**分析/对账/备份/导出/审计能力整体缺位**，仍是"记账工具"而非"经营系统" |

**一句话**：事务与防注入底子好，但库存正确性、采购 UI、鉴权、经营分析是四处系统性短板，建议优先收敛。

## 二、已验证的致命 / 严重问题（按模块）

### A. 后端 Rust（库存 / 数据正确性 / 生产安全）

#### 🔴 C1【致命】`update_purchase_order` 反向还原库存写死 `stock_grams` 且按原始全量扣减 → 计件错乱 + 负库存
- 位置：`src-tauri/src/commands/inventory.rs:909`（反向还原）、`:983`（重建，已正确用 `stock_field`）
- 证据：
  ```rust
  // 反向还原（步骤4.2）——写死 stock_grams
  "UPDATE products SET stock_grams = stock_grams - ? WHERE id = ?"
  // 重建（步骤8）——按类型选择
  let stock_field = if product_type == "weight" { "stock_grams" } else { "stock_units" };
  ```
- 影响：① 计件商品（base_unit=pcs）入库增量写入 `stock_units`，修改采购单却从 `stock_grams` 减 → 计件真实库存永不还原、称重字段被错误扣减；② 还原按 `old_item.grams`（原始采购全量）扣减，**不扣除已被销售/报损/退货消耗的部分** → 例：采购 1000g 卖出 400g（剩 600），改单删批次再扣 1000g → `600-1000=-400`，**库存变负、业务数据损坏**。
- 修复：反向还原必须与重建对称（按 `product_type` 选 `stock_field`）；还原量应基于批次**当前剩余**（`remaining_grams`），并加 `WHERE stock_xxx - ? >= 0` 负值校验。

#### 🔴 C2【致命】`damage_out` / `adjust_stock` 仅操作 `stock_grams`，计件商品库存完全不处理
- 位置：`inventory.rs:480-495`（damage_out）、`:548-564`（adjust_stock）
- 证据：`damage_out` 全程 `SELECT stock_grams` / `UPDATE ... stock_grams` / 错误提示"当前库存 {}g"，**完全无视 `product_type`**；`adjust_stock` 同样只读写 `stock_grams`。对比 `purchase_in_impl`（:361）已正确用 `stock_field`，此处属明显遗漏。
- 影响：对**计件商品**做报损出库 / 盘点调整 → 既不减少 `stock_units`，又错误改动对计件无意义的 `stock_grams`；`deduct_from_batches` 仅调 `remaining_grams`，计件主表无补偿。报损/盘点对计件商品**完全失效且字段错乱**。
- 修复：与入库一致，按 `product_type` 选择 `stock_grams`/`stock_units`（含 `adjust_stock` 的 `new_balance` 计算与 `damage_out` 的库存检查/扣减）。

#### 🟠 C3【严重】`seed_demo_data` 无生产门禁却清空全库 → 生产环境保护被绕过
- 位置：`commands/dev_data.rs:79`（seed）、`:110`（调用 `clear_business_tables`）、`:835`（`clear_all_data` 才有 `cfg!(debug_assertions)` 门禁）
- 证据：`clear_all_data` 在 release 被 `if !cfg!(debug_assertions) { return Err(...) }` 拦截；但 `seed_demo_data` **无此门禁**，却在执行前 `clear_business_tables(&conn, &rollback)?` 清空全部业务表（商品/会员/采购/销售/退货/供应商付款等）。
- 影响：**release 构建中 `clear_all_data` 被拒，但 `seed_demo_data` 仍可执行并把真实生产数据清空再灌演示数据**，等于生产安全形同虚设。
- 修复：给 `seed_demo_data` 加相同 `cfg!(debug_assertions)` 编译期门禁；理想情况下这两个命令在 release 中不注册到 `invoke_handler`。

#### 🟡 G1 / G2【一般】采购金额与供应商余额未 `round2`，f64 累加漂移
- 位置：`inventory.rs:336`（purchase_in_impl `subtotal = unit_price*quantity` 后直接累加）、`:966`（update_purchase_order）；`supplier_payments.rs:336`（`balance = total_purchase - total_paid - total_return` 未 round2）
- 修复：统一 `crate::utils::money::round2(...)`，与销售侧策略一致。

#### 🟡 G4【一般】无会员时 `points_deduct>0` 仍扣减实付金额却无积分来源校验
- 位置：`sales.rs:342-366`。积分余额校验仅在 `member_id` 存在时执行；无会员却传 `points_deduct>0` → 金额被减（凭空优惠）且无任何会员积分被扣。
- 修复：无会员时 `points_deduct` 必须为 0 并校验。

#### 🟡 G5【一般】`hold_order` 写入 `pay_status='pending'` 与详情返回 `'unpaid'` 不一致
- 位置：`sales.rs:548`（INSERT 写 `pending`）vs `:684`（返回 `unpaid`），测试 `:1387` 亦断言 `pending`。前后端语义不一致。修复：统一为 `unpaid`。

#### 🟡 G6【一般】`pay_method='memberBalance'` 但无 `member_id` 时静默不扣款
- 位置：`sales.rs:432`（`if` 位于 `if let Some(ref mid)=input.member_id` 块内）。前端传 `memberBalance` 却无 `member_id` → 订单记 `memberBalance` 但未扣任何余额，账目与支付记录脱节。修复：`memberBalance` 必须要求 `member_id` 非空。

#### 🟢 P1【架构】全局 `Mutex<Connection>` 串行化所有 DB 操作
- 位置：`db/mod.rs`（`get_conn()` 返回独占 `MutexGuard`）。正确性无虞，但并发吞吐为零，高并发开单会排队。建议后续评估连接池/多连接（属架构调整，需单独确认）。

> 正面：经全量审查**未发现任何 SQL 注入点**（列名均为代码常量，值均参数化）；命令路径无 `.unwrap()/.expect()` panic；事务普遍 `BEGIN EXCLUSIVE` + 回滚闭包。这是底子好的部分。

### B. 前端 Vue / TS（业务闭环 / 安全 / 体验）

#### 🔴 F1【致命】库存「采购入库」弹窗无法选择单位，提交校验永远不通过 → 采购入库完全不可用
- 位置：`src/views/inventory/index.vue:142-167`（弹窗仅含 商品/入库数量/采购单价/经手人/备注，**无单位控件**）、`:422`（`unitId:''`）、`:433`（`if (!items[0].unitId) { warning('请选择入库单位'); return }`）
- 影响：因界面无单位选择控件，`unitId` 永远为空，校验永远失败——**采购入库无法通过界面完成，核心入库流程阻断**。
- 修复：弹窗增加"入库单位"下拉（`getProductUnits` 加载并写回 `purchaseForm.items[0].unitId`）。

#### 🟠 F2【严重】采购入库无供应商选择，`supplierId` 恒为 `undefined`
- 位置：`inventory/index.vue:418`（`supplierId: undefined`，弹窗无供应商字段）。即便修了单位，采购单仍缺供应商，后端很可能校验失败。
- 修复：新增供应商 `n-select`（`useSupplierStore.loadActiveSuppliers()`），绑定 `purchaseForm.supplierId`。

#### 🟠 F3【严重·安全】登录无真实鉴权，密码以 base64 明文存储
- 位置：`src/views/auth/Login.vue:224-236`（`handleLogin` 接受任意账号密码 → `localStorage.setItem('tea-logged-in','1')` 直接跳转）、`:152`（密码 `btoa` base64 存 localStorage）、`router/index.ts`（守卫仅判 `tea-logged-in==='1'`，该 flag 可被任意方式写入绕过）、页脚明示"任意账号密码即可进入演示"。
- 影响：鉴权形同虚设；base64 非加密，任意可读出明文密码。
- 说明：当前为演示壳，属"单机本地版"可接受范围，但要做"业务信息化/安全"必须升级。→ **归入新功能/安全，需确认后实施**。

#### 🟡 S1【一般·显示口径】会员折扣"标签"与"实际"不一致
- 位置：`members/MemberList.vue:218-219`（`getDiscountLabel`：金卡 `'8折'`、银卡 `'9折'`）vs `api/members.ts:101-107`（`getMemberDiscountRate`：金卡 `0.9`、银卡 `0.95`）
- 澄清（已复核）：收银实际计算 `sales/index.vue:327` 与后端 `sales.rs:210` 均用 `0.9/0.95`（即 9折/95折），**实际收款正确**；但列表/抽屉**标签错误显示为 8折/9折**，易引发顾客与店员对"该打几折"的误解与纠纷。
- 修复：统一折扣标签为 9折/95折（抽取单一常量来源，避免 `getDiscountLabel` 与 `getMemberDiscountRate` 两处漂移）；`MemberDetail.vue` 同步。

#### 🟡 S2【一般】收银 `SaleOrderInput` 未携带 `discountAmount` / `pointsDeduct`
- 位置：`sales/index.vue:539-547` 构造 `SaleOrderInput`（仅 `items/memberId/payMethod`）；`types/index.ts` `SaleOrderInput` 定义。
- 澄清：后端 `create_sale_order` 按 `member_id` **重算**折扣（与前端一致），故折扣金额未丢失；但若将来加"手动折扣/积分抵现"UI，当前结构无法传递。积分抵扣目前前端无对应 UI。
- 建议：保持后端为折扣权威源；如需前端手动折扣/积分，扩展 `SaleOrderInput` 并让后端以传入值为准（需前后端协同，建议纳入功能完善阶段）。

#### 🟠 S4【严重】取单（resumeOrder）重建会员对象时 `points/balance` 硬编码为 0
- 位置：`sales/index.vue:624-626`（`currentMember = { ..., points:0, balance:0 }`）。
- 影响：挂单只记 `memberId/memberName`，取单后丢弃真实积分与余额 → 用"会员卡"支付时 `validatePayMethod` 用 `balance=0` 判余额不足**误拒**；会员积分/等级信息丢失，影响折扣与积分累计。
- 修复：取单时按 `order.memberId` 调 `getMemberDetail` 取回真实会员对象（含 `balance/points/level`）。

#### 🟠 S5【严重·安全】打印回退 `buildReceiptHTML` 未做 HTML 转义 → XSS
- 位置：`utils/print.ts:233/270/294/299`（`${item.productName}`、`${shopName}`、`${order.memberName}`、`${order.orderNo}` 直接拼入 HTML）。正常走模板引擎（`renderTemplateHTML` 已转义），仅当模板引擎抛错时回退到此路径。
- 影响：若商品名含 `<img src=x onerror=...>` 等，会在打印 iframe 中执行。
- 修复：`buildReceiptHTML` 所有动态字段统一经 `esc()` 转义（复用 `printTemplate.ts` 的 `esc`）。

#### 🟠 S6【严重】采购「详情」路由指向空白页
- 位置：`src/views/purchase/PurchaseDetail.vue`（0 字节）；`PurchaseList.vue:goDetail`（`router.push('/purchase/'+row.id')`）。
- 影响：点击采购单"详情"跳转后页面空白，无法查看采购明细。
- 修复：补全 `PurchaseDetail.vue`（参照 `ReturnDetail.vue` 结构）。

#### 🟡 N1【一般】设置不持久化，店铺名刷新即丢失
- 位置：`stores/settings.ts:29-48`（`saveSettings/loadSettings` 为 TODO 空实现）。刷新后 `shopName` 回默认"茶易管"，**打印小票店铺名永远显示"茶易管"**。→ 需后端 `get_settings/save_settings` 支持。

#### 🟡 N2【一般】编辑采购单无法修改付款状态
- 位置：`PurchaseForm.vue:handleSubmit` → `api/purchases.ts:updatePurchaseOrder(id, input)`（input 无 `paymentStatus`）。采购单付款状态无法通过"编辑"变更，付款工作流断裂。

#### 🟡 N3【一般】金额用 f64 浮点运算，存在精度误差风险
- 位置：`utils/price.ts`、`sales/index.vue:321-342`（`total/discount/final/change` 均为 `number` 运算）。`0.1*3` 类产生 `0.30000000000000004`，找零/对账可能 1 分误差累积。建议内部用整数"分"或 `decimal.js`。

#### 🟡 N4【一般】结算成功后未刷新库存/商品 store
- 位置：`sales/index.vue:549-562`。结算后仅清空本地购物车，切到"库存管理"看到旧库存，需手动刷新。

#### 🟡 N5【一般】退货编辑 `conversion = grams/quantity` 可能除零
- 位置：`returns/ReturnForm.vue:441-444`。`quantity===0` 时 `Infinity`；`remainingGrams` 用原批次值而非当前剩余量。

#### 🟡 N6【一般】设置页"初始化数据库"按钮为空实现
- 位置：`settings/index.vue:182-184`（`initDatabase` 仅 `// TODO`）。点击无反馈。

#### 🟢 其他建议
- A1 `stores/index.ts` 未统一导出 `usePrintTemplatesStore/useTabsStore/useThemeStore`。
- A2 `barcodes/index.vue` 批次/条码查询 tab 为 `message.info('开发中')` 占位。
- A3 `dashboard/TodayStats.vue` 四张卡片为**硬编码 Mock**（注释明示"实际项目替换为 API 数据"），店长看到的经营指标是假的。
- A4 `MemberDetail.vue` 直接显示 `0.9` 原始比率，未转"9折"。
- A5 登录态 `tea-logged-in` 永不清除，UserMenu 退出为禁用占位。

## 三、业务信息化覆盖盲区（规格对照）

对照 `specs/` 规划功能与代码实际实现，核心盲区如下（详细见子报告）：

| 盲区 | 现状 | 影响 |
|------|------|------|
| **经营报表 / 数据分析** | 无任何销售统计、毛利、库存周转、畅滞销分析；Dashboard 为 Mock | 店长看不到真实经营指标，系统只是"记账工具" |
| **销售历史查询** | 后端 `sales.rs` **无 `get_sale_orders`**，连"今日卖了什么"都无法查 | 报表与售后查询的数据底座不存在 |
| **数据备份 / 恢复** | 设置页按钮仅 `message.info('备份功能开发中')` | 单机 SQLite 存在丢数风险，不满足 PRD 非功能需求 |
| **供应商付款 / 对账 UI** | 后端 `supplier_payments` 命令已写好（付款/流水/余额/财务流水），但**无路由/菜单/页面** | 采购付款状态与应付账款断在 UI 层 |
| **会员深度运营** | 无 RFM、无积分抵现规则、无等级自动晋升、无生日/复购营销 | 私域复购核心能力缺位 |
| **条码 / 批次查询** | 除"能生成图"外，批次查询/批量打印/条码查询全是 `开发中` 占位 | M7 剩余 60% 未落地 |
| **数据导出 / 审计 / 权限分级** | 均无 | 离线对账、报税、操作留痕、角色权限缺位 |

> 覆盖度评分 **6/10**：日常营业事务处理基本可用（进销存+收银+会员+打印），但"看清/对清/备出/导出/审计"整体缺位。

## 五、结论
系统**事务处理与防注入底子扎实**，但存在三处系统性短板：
1. **库存正确性**（C1/C2）——计件/称重字段处理不一致、采购单修改可造负库存，属致命数据风险；
2. **采购入库 UI 不可用 + 取单丢会员余额 + 采购详情空白**（F1/F2/S4/S6）——核心营业链路断裂；
3. **经营分析/对账/备份/导出整体缺位**——离"业务信息化"尚有距离。
