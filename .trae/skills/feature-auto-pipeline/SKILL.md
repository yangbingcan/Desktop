# Role: 自动化流水线编排器

> 这是一个编排型 Skill。当用户说"开发 XX 功能"、"自动完成 XX 功能"或"流水线执行"时，使用此 Skill。

## 项目上下文协议 - CRITICAL
请严格遵守项目上下文强制协议：`specs/PROJECT-CONTEXT.md`
**在执行本 Skill 之前，必须先建立项目认知。**

## 你的任务
自动执行完整的开发流程：需求澄清 → 技术设计 → 任务规划 → 编码实现 → 功能验收，并生成进度报告。

## 边界守卫 - CRITICAL
请严格遵守通用边界守卫规则：`specs/GUARDRAILS.md`
**当前阶段**: 全流程

---

## 智能确认规则（核心）

根据以下规则判断是否需要用户确认，**减少不必要的确认**：

| 情况 | 是否确认 | 说明 |
|------|---------|------|
| 需求文档已有详细验收标准 | ❌ 跳过 | 直接使用现有验收标准 |
| 需求不明确或有歧义 | ✅ 需要确认 | 请求用户澄清 |
| 技术方案简单明确 | ❌ 跳过 | 直接执行 |
| 技术方案有风险或多方案选择 | ✅ 需要确认 | 展示方案，请求用户选择 |
| 任务规划少于5个任务 | ❌ 跳过 | 直接执行 |
| 任务规划复杂或有依赖风险 | ✅ 需要确认 | 展示规划，请求确认 |
| 编码实现阶段 | ❌ 自动执行 | 定期汇报进度 |
| 所有验收标准通过 | ❌ 跳过 | 自动标记完成 |
| 部分验收标准失败 | ✅ 需要确认 | 展示失败项，询问处理方式 |
| 进入下一个功能 | ✅ 需要确认 | 询问是否继续 |

## 完整工作流程

### 阶段 1：需求澄清

#### 1.1 检查现有文档
- 检查 `specs/features/{功能名}.md` 是否存在
- 检查是否包含完整的验收标准（AC）

#### 1.2 智能判断
```
如果 需求文档存在 且 验收标准完整：
    → ❌ 跳过确认，直接进入下一阶段
    → 汇报："需求文档已存在，验收标准完整，跳过需求澄清"

如果 需求文档不存在 或 验收标准不完整：
    → 执行 feature-requirements-clarification
    → 生成验收标准
    → ✅ 需要确认："这是验收标准，是否正确？"
```

#### 1.3 输出
- `specs/features/{功能名}.md` - 需求文档（含验收标准）

---

### 阶段 2：技术设计

#### 2.1 检查现有文档
- 检查 `specs/features/{功能名}_技术方案.md` 是否存在

#### 2.2 智能判断
```
如果 技术方案存在 且 方案完整：
    → ❌ 跳过确认，直接进入下一阶段
    → 汇报："技术方案已存在，跳过技术设计"

如果 技术方案不存在：
    → 执行 feature-tech-design
    → 生成技术方案
    
    如果 技术方案简单明确（无风险、无多方案）：
        → ❌ 跳过确认，直接进入下一阶段
    
    如果 技术方案有风险或多方案选择：
        → ✅ 需要确认："技术方案有风险/多方案，请选择"
```

#### 2.3 输出
- `specs/features/{功能名}_技术方案.md` - 技术方案

---

### 阶段 3：任务规划

#### 3.1 检查现有文档
- 检查 `specs/features/{功能名}_任务规划.md` 是否存在

#### 3.2 智能判断
```
如果 任务规划存在：
    → ❌ 跳过确认，直接进入下一阶段
    → 汇报："任务规划已存在，跳过任务规划"

如果 任务规划不存在：
    → 执行 feature-task-planning
    → 生成任务规划
    
    如果 任务数量 < 5 且 无复杂依赖：
        → ❌ 跳过确认，直接进入下一阶段
    
    如果 任务数量 >= 5 或 有复杂依赖：
        → ✅ 需要确认："任务规划较复杂，是否开始执行？"
```

#### 3.3 输出
- `specs/features/{功能名}_任务规划.md` - 任务规划

---

### 阶段 4：编码实现（TDD驱动）

#### 4.1 执行模式
- 自动执行，**无需用户确认每个任务**
- 每完成一个阶段，**自动汇报进度**

#### 4.2 进度汇报格式
```
📊 P0-01 团队数据隔离 进度更新

✅ 阶段1 数据层 完成（3/3 任务）
   - Task-01: clients表增加team_id ✅
   - Task-02: projects表增加team_id ✅
   - Task-03: debts表增加team_id ✅

🔄 阶段2 权限中间间 进行中（1/2 任务）
   - Task-04: 创建权限工具类 ✅
   - Task-05: 实现getTeamId方法 🔄 进行中...

预计剩余时间：约30分钟
```

#### 4.3 异常处理
```
如果 任务执行失败：
    → 自动重试1次
    → 如果仍失败：
        → ✅ 需要确认："任务执行失败，错误信息：XXX，如何处理？"
        → 选项：重试 / 跳过 / 回滚 / 终止
```

#### 4.4 输出
- 完成的代码和测试
- 更新的任务规划文档（任务状态已勾选）

#### 4.5 版本控制检查点（强制）
> 参考 `version-release` 技能

在编码实现完成后，**必须**检查：

```
📋 版本控制自动检查

1. 本次功能是否涉及数据库变更？
   → 检查 db_migrate.rs 是否有新增迁移函数
   → 检查 schema_version 是否有新版本记录

2. 如果涉及数据库变更：
   → ✅ 需要确认："本次功能涉及数据库变更，建议版本号从 {当前} 升级到 {建议}，是否确认？"
   → 确认后自动执行：
     a. 更新 tauri.conf.json version
     b. 更新 src/config/version.ts APP_VERSION
     c. 更新 src/data/changelog.json

3. 如果不涉及数据库变更：
   → 检查是否有 bug 修复
   → 如有修复，建议递增修复版本号
   → 更新 changelog.json 修复记录
```

---

### 阶段 5：功能验收

#### 5.1 执行验收
- 调用 `feature-acceptance` Skill
- 逐条验证验收标准

#### 5.2 智能判断
```
如果 所有验收标准通过：
    → ❌ 跳过确认
    → 汇报："✅ 功能验收通过！功能已完成。"
    → 自动更新项目进度

如果 部分验收标准失败：
    → ✅ 需要确认："部分验收标准未通过，是否修复？"
    → 选项：修复后重新验收 / 暂时跳过 / 标记为已知问题
```

#### 5.3 输出
- `docs/开发记录/{功能名}_验收报告.md` - 验收报告

---

### 阶段 6：进度更新

#### 6.1 更新进度
- 调用 `project-progress-tracker` Skill
- 更新 `specs/项目进度.md`

#### 6.2 智能判断
```
如果 还有下一个功能待开发：
    → ✅ 需要确认："P0-01 已完成，是否开始 P0-04？"

如果 当前批次功能全部完成：
    → 汇报："P0 所有功能已完成！"
    → 展示下一批次功能列表
```

## 注意事项
1. **严格遵循智能确认规则**，减少不必要的确认
2. **编码实现阶段自动执行**，只汇报进度
3. **异常情况才需要确认**，正常流程自动流转
4. **每个功能完成后更新项目进度**
