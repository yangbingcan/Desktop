# 综合代码审核（10维度框架）

> **适用场景**：对项目代码进行系统性、多维度的深度审核，产出结构化问题报告与改进方案。
> **设计原则**：分层审核 × 技术栈聚焦 × 自动化优先 × 精确分级 × 可追踪闭环

---

## 触发条件

**必须调用此技能的场景：**
- 功能级流程：`feature-implementation`（编码实现）完成后、`feature-acceptance`（功能验收）之前
- 发布流程：`version-release` 编译检查之前
- BUG修复：`bugfix-workflow` 修复完成后验证
- 用户明确要求代码审核、代码审查、质量检查
- 重大架构变更后

**不适用场景：**
- 简单 diff 审查 → 使用 `TRAE-code-review`
- 单文件/单函数审查 → 直接人工审查
- 需求阶段/设计阶段 → 禁止产出代码审核结果（违反流程铁律）

## 第0步：审核准备（前置条件）

> ⚠️ 未完成前置准备直接开始审核视为流程违规。

### 0.1 项目文档读取

| 序号 | 必读项 | 路径 | 目的 |
|------|--------|------|------|
| 1 | 边界守卫 | `specs/GUARDRAILS.md` | 理解流程约束和阶段边界 |
| 2 | 项目上下文 | `specs/PROJECT-CONTEXT.md` | 理解项目核心原则 |
| 3 | 项目配置 | `specs/project_config.md` | 确认技术栈、版本号、目录结构 |
| 4 | 开发规范 | `specs/开发规范.md` | 理解代码规范要求 |
| 5 | 版本文档 | `specs/releases/v{当前版本}.md` | 了解当前版本变更范围 |
| 6 | docs/ 目录 | `docs/**/*` | 了解系统概述和开发记录 |

### 0.2 技术栈确认

根据 `project_config.md` 确认技术栈，激活对应的专项检查项：

| 技术栈 | 激活的专项检查 |
|--------|---------------|
| **React 18** | Hook 规则、组件生命周期、状态管理、渲染性能 |
| **TypeScript** | 类型安全、any 使用、泛型约束、类型守卫 |
| **Rust** | unwrap/panic、生命周期、错误处理（Result/Option）、unsafe |
| **Tauri 2** | IPC 安全、权限配置、资源访问、窗口安全 |
| **Ant Design 5** | 组件 API 使用、主题定制、表单校验 |
| **Zustand** | Store 设计、订阅优化、持久化 |
| **SQLite** | 迁移安全、事务完整性、索引优化、SQL 注入 |
| **TailwindCSS** | 类名冗余、响应式断点、自定义主题一致性 |

### 0.3 已有问题了解

- 扫描项目中已有的 `TODO`、`FIXME`、`HACK`、`XXX` 注释
- 读取上一轮审核报告（如存在），确认遗留问题
- 检查 `docs/` 目录中的已知问题记录

### 0.4 审核范围确认

使用 `AskUserQuestion` 确认审核范围：

| 选项 | 说明 |
|------|------|
| **全量审核** | 整个代码库，适用于发版前 |
| **增量审核** | 指定目录或文件，适用于功能完成后 |
| **安全专项** | 重点维度7B、9、10，适用于安全审计 |
| **性能专项** | 重点维度7A，适用于性能优化 |
| **架构专项** | 重点维度5、9，适用于架构重构后 |

## 审核维度（10维度）

### 维度1：代码完整性与功能闭环

**目标**：确保所有功能模块完整实现，不存在功能缺口或半成品代码。

| 序号 | 检查项 | 严重程度 | 技术栈特定检查 |
|------|--------|---------|---------------|
| 1.1 | 是否存在未完成的代码片段、TODO/FIXME 注释 | 🔴 严重 | — |
| 1.2 | 核心业务流程是否形成完整闭环（输入→处理→输出→反馈） | 🔴 严重 | — |
| 1.3 | 是否存在"半拉子"功能（只实现部分场景，关键路径缺失） | 🔴 严重 | — |
| 1.4 | 所有对外暴露的接口/函数/方法是否有对应实现（无空实现或占位符） | 🔴 严重 | — |
| 1.5 | 错误场景是否有对应的用户反馈（Toast/Modal/状态提示） | 🟡 重要 | React：ErrorBoundary；Rust：错误是否通过 IPC 传递到前端 |
| 1.6 | 异步操作是否有加载状态和完成状态处理 | 🟡 重要 | React：Suspense/loading 状态；Rust：异步命令是否返回结果 |
| 1.7 | 组件卸载时是否清理副作用（定时器、订阅、事件监听） | 🟡 重要 | React：useEffect 清理函数；Rust：Drop trait 实现 |
| 1.8 | Tauri IPC 命令是否前后端成对存在（前端 invoke ↔ 后端 #[tauri::command]） | 🔴 严重 | Tauri：检查 invoke 调用与 command 定义的对应关系 |

**自动化检查**：
```bash
# 扫描 TODO/FIXME
grep -rn "TODO\|FIXME\|HACK\|XXX" --include="*.ts" --include="*.tsx" --include="*.rs" src/ src-tauri/src/
# 检查空函数体
grep -rn "function.*{}\|=>.*{}" --include="*.ts" --include="*.tsx" src/
# 检查 Rust 空实现
grep -rn "todo!()\|unimplemented!()" --include="*.rs" src-tauri/src/
```

**目标**：消除重复代码，保持代码简洁，避免过度设计。

| 序号 | 检查项 | 严重程度 | 技术栈特定检查 |
|------|--------|---------|---------------|
| 2.1 | 是否存在完全重复或逻辑高度相似的代码块 | 🟡 重要 | — |
| 2.2 | 是否存在可合并、抽象或复用的函数/类/组件 | 🟡 重要 | React：相似组件是否可提取为通用组件；Rust：相似函数是否可用泛型统一 |
| 2.3 | 是否存在不必要的变量声明、导入语句、注释和空行 | 🟢 一般 | TypeScript：未使用的 import；Rust：未使用的 use 声明 |
| 2.4 | 是否存在过度设计（复杂设计模式但需求不需要） | 🟡 重要 | — |
| 2.5 | 条件判断、循环结构是否可简化 | 🟢 一般 | — |
| 2.6 | 组件是否过大需要拆分（>300行建议拆分） | 🟡 重要 | React：单组件行数；Rust：单函数行数 |
| 2.7 | Store 是否存在冗余状态（派生状态应使用 selector） | 🟡 重要 | Zustand：是否存在可由其他状态计算得出的冗余 state |
| 2.8 | CSS 类名是否存在冗余（Tailwind 重复类名串） | 🟢 一般 | TailwindCSS：相同类名组合是否可提取为 @apply 或组件 |

### 维度3：异常处理与错误边界

**目标**：确保所有异常场景都有妥善处理，不会导致程序崩溃或数据丢失。

| 序号 | 检查项 | 严重程度 | 技术栈特定检查 |
|------|--------|---------|---------------|
| 3.1 | 所有可能抛出异常的代码块是否有 try-catch/Result 处理 | 🔴 严重 | Rust：是否使用 Result 而非 panic；TypeScript：async 函数是否 catch |
| 3.2 | 异常捕获粒度是否合理（不过宽也不过窄） | 🟡 重要 | — |
| 3.3 | 异常信息是否清晰、准确，包含足够上下文便于调试 | 🟡 重要 | Rust：错误类型是否实现 thiserror/anyhow；TS：是否包含错误码和描述 |
| 3.4 | 资源释放是否正确（文件/数据库连接/网络连接） | 🔴 严重 | Rust：RAII 是否正确；TS：finally 块或 cleanup 函数 |
| 3.5 | 边界条件处理是否完整 | 🔴 严重 | — |
| 3.5a | 空值（null/undefined/None）处理 | 🔴 严重 | TypeScript：可选链和空值合并；Rust：Option 处理 |
| 3.5b | 空集合、空字符串处理 | 🟡 重要 | — |
| 3.5c | 数值边界（最大值/最小值/零值/NaN）处理 | 🟡 重要 | — |
| 3.5d | 数组越界、索引越界处理 | 🔴 严重 | Rust：是否使用 .get() 而非直接索引；TS：是否检查 length |
| 3.5e | 类型转换异常处理 | 🟡 重要 | TypeScript：类型守卫；Rust：From/TryFrom |
| 3.6 | Rust：是否存在 unwrap()/expect() 在非测试代码中 | 🔴 严重 | 生产代码中的 unwrap 视为严重问题，应使用 match/unwrap_or/unwrap_default |
| 3.7 | React：ErrorBoundary 是否覆盖关键组件树 | 🟡 重要 | 路由级别和关键业务组件是否被 ErrorBoundary 包裹 |
| 3.8 | Tauri：IPC 调用是否处理了命令不存在/超时/序列化失败 | 🟡 重要 | invoke 调用是否 catch 所有错误路径 |
| 3.9 | 错误处理逻辑本身是否存在漏洞（catch 块中的异常） | 🔴 严重 | — |

**自动化检查**：
```bash
# Rust unwrap 检测（排除测试）
grep -rn "\.unwrap()" --include="*.rs" src-tauri/src/ | grep -v "test"
# Rust panic 检测
grep -rn "panic!\|todo!\|unimplemented!" --include="*.rs" src-tauri/src/ | grep -v "test"
# TypeScript 空 catch 块
grep -rn "catch.*{}" --include="*.ts" --include="*.tsx" src/
```

**目标**：识别性能瓶颈和安全漏洞，确保系统高效且安全。

| 序号 | 检查项 | 严重程度 | 技术栈特定检查 |

## 严重程度分类标准

### 🔴 严重（Critical）— 必须立即修复

**判定标准**（满足任一即属严重）：
- 会导致程序崩溃、数据丢失、数据损坏
- 存在安全漏洞（SQL 注入、XSS、认证绕过等）
- 核心业务功能无法使用
- 金额计算错误
- 并发安全问题（竞态条件、死锁）
- 生产代码中的 Rust unwrap()/panic!()
- 前后端数据模型不一致

**修复时限**：阻塞发布，必须在本版本修复

### 🟡 重要（Major）— 应当修复

**判定标准**（满足任一即属重要）：
- 影响功能正确性但不会导致崩溃
- 性能明显下降（慢查询、内存泄漏风险）
- 代码可维护性差（过度耦合、缺少注释、命名混乱）
- 异常处理不完善（空 catch、错误信息不清晰）
- 缺少必要的测试覆盖
- 架构设计不合理但不影响当前功能

**修复时限**：建议在本版本修复，最迟下版本

### 🟢 一般（Minor）— 建议改进

**判定标准**（满足任一即属一般）：
- 代码风格问题（命名、格式、注释）
- 轻微冗余但不影响可维护性
- 优化建议（非必要的性能优化）
- 文档补充建议

**修复时限**：可排入后续迭代
