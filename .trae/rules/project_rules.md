# 开发流程规范

> **对话开始必须读取：** `specs/GUARDRAILS.md`、`specs/PROJECT-CONTEXT.md`、`specs/project_config.md`、`docs/` 目录下所有文档

---

## 一、流程地图

### 1.1 项目级流程（一次性）

项目启动时走一遍，完成后进入功能级循环。

```
[1]协议初始化 → [2]需求澄清 → [3]产品概述 → [4]技术选型 → [5]目录结构 → [6]代码规范 → [7]路线图规划 → [8]项目初始化
```

| 阶段 | 触发条件 | 做什么 | 产出 | 对应技能 |
|------|---------|--------|------|---------|
| 协议初始化 | 新项目/首次使用 | 创建目录结构和协议文件 | specs/ 目录 | `project-protocol-init` |
| 需求澄清 | 项目启动 | 苏格拉底式提问，明确核心价值 | 项目描述文档 | `project-requirements-clarification` |
| 产品概述 | 需求明确后 | 定义愿景、模块、用户、场景 | 产品概述文档 | `project-product-overview` |
| 技术选型 | 产品概述确定后 | 选择技术栈 | 技术栈文档 | `project-tech-stack` |
| 目录结构 | 技术栈确定后 | 设计目录结构 | 目录结构文档 | `project-structure` |
| 代码规范 | 技术栈确定后 | 定义代码风格、Git规范 | 代码规范文档 | `project-dev-standards` |
| 路线图规划 | 产品概述+技术栈确定后 | 规划开发顺序和里程碑 | 路线图文档 | `project-roadmap-planning` |
| 项目初始化 | 路线图确定后 | 创建项目骨架代码 | 可运行项目 | `project-initialization` |

### 1.2 功能级流程（循环）

每个功能走一遍，可由 `feature-auto-pipeline` 自动编排。

```
[F1]需求澄清 → [F2]技术设计 → [F3]任务规划 → [F4]编码实现(TDD) → [F5]功能验收 → [F6]进度更新 → 下一个功能
```

| 阶段 | 触发条件 | 做什么 | 产出 | 对应技能 |
|------|---------|--------|------|---------|
| 需求澄清 | 新功能开发时 | 定义验收标准 | 功能需求文档 | `feature-requirements-clarification` |
| 技术设计 | 验收标准确定后 | 设计API、数据库、核心逻辑 | 技术方案文档 | `feature-tech-design` |
| 任务规划 | 技术方案确定后 | 拆解为可执行任务 | 任务清单 | `feature-task-planning` |
| 编码实现 | 任务清单确定后 | TDD驱动开发 | 代码+测试 | `feature-implementation` |
| 功能验收 | 编码完成后 | 逐条验证验收标准 | 验收报告 | `feature-acceptance` |
| 进度更新 | 功能验收后 | 更新项目进度 | 进度文档 | `project-progress-tracker` |

### 1.3 修复流程（随时触发）

```
[B1]复现 → [B2]定位 → [B3]修复 → [B4]验证 → [B5]报告 → 版本文档更新
```

| 阶段 | 触发条件 | 做什么 | 产出 | 对应技能 |
|------|---------|--------|------|---------|
| BUG修复 | 发现BUG时 | 复现→定位→修复→验证 | 修复报告 | `bugfix-workflow` |

### 1.4 发布流程（用户确认后）

```
[R1]编译检查 → [R2]版本号同步 → [R3]构建 → [R4]验证 → [R5]文档更新 → [R6]发布记录
```

| 阶段 | 触发条件 | 做什么 | 产出 | 对应技能 |
|------|---------|--------|------|---------|
| 版本发布 | 用户确认发版 | 编译→同步版本号→构建→验证 | 安装包 | `version-release` |

### 1.5 流程流转规则

1. **项目级流程**必须按顺序执行，不可跳过
2. **功能级流程**可由 `feature-auto-pipeline` 自动编排，也可手动逐步调用
3. **修复流程**可在任何阶段触发，修复完成后回到原流程继续
4. **发布流程**仅在用户明确确认后触发，不可自动执行
5. 已有文档的阶段可跳过（如需求文档已存在且完整，跳过需求澄清）

### 1.6 流程强制执行机制

#### 1.6.1 流程状态追踪

每次对话开始时，必须执行以下操作：

1. 读取 `specs/` 目录下的项目文档，确认当前项目所处流程阶段
2. 在回复开头声明当前流程状态，格式：`📍 当前流程：[项目级/功能级] - [阶段名]`
3. 如果项目级流程未完成，禁止进入功能级流程（修复流程除外）

#### 1.6.2 阶段门禁（Stage Gate）

每个阶段完成前，必须满足以下条件才能进入下一阶段：

| 阶段 | 必须产出 | 门禁检查 |
|------|---------|---------|
| 协议初始化 | specs/ 目录 + 三个协议文件 | 文件存在且内容完整 |
| 需求澄清 | `specs/需求澄清.md` | 文档包含核心价值、目标用户、核心功能 |
| 产品概述 | `specs/产品概述.md` | 文档包含愿景、模块、用户、场景 |
| 技术选型 | `specs/技术选型.md` | 文档包含技术栈选择及理由 |
| 目录结构 | `specs/目录结构.md` | 文档包含完整目录树 |
| 代码规范 | `specs/代码规范.md` | 文档包含命名、格式、Git规范 |
| 路线图规划 | `specs/路线图.md` | 文档包含里程碑和功能优先级 |
| 项目初始化 | 可运行项目骨架 | 项目可正常启动 |

#### 1.6.3 跳步拦截规则

**以下行为视为严重违规，必须主动拦截：**

1. **跨阶段产出** — 在需求阶段写代码、在设计阶段写实现、在规划阶段执行操作
2. **跳过阶段** — 未经完成当前阶段直接进入后续阶段
3. **省略文档** — 完成阶段工作但未产出对应文档
4. **被动等待** — 流程规定下一步是什么时，询问用户"需要继续吗"而不是直接执行

**拦截方式：**

- 发现自己即将越界时，立即停止并声明：`⚠️ 流程拦截：当前处于[阶段]，不允许产出[越界内容]。请先完成[当前阶段]的[必要产出]。`
- 发现跳步时，回退到被跳过的阶段继续执行

#### 1.6.4 对话开始自检清单

每次新对话开始时，必须逐项检查：

```
□ 1. 读取 specs/GUARDRAILS.md
□ 2. 读取 specs/PROJECT-CONTEXT.md
□ 3. 读取 specs/project_config.md
□ 4. 扫描并读取 docs/ 目录下所有文档（系统概述、开发记录、技术文档等）
□ 5. 扫描 specs/ 目录，确认项目级流程完成到哪一步
□ 6. 声明当前流程状态
□ 7. 从当前阶段继续执行，不跳步
```

#### 1.6.5 违规判定

| 场景 | 判定 | 级别 |
|------|------|------|
| 对话开始未读取协议文件 | 严重违规 | 🔴 |
| 对话开始未读取 docs/ 目录文档 | 严重违规 | 🔴 |
| 跳过项目级流程阶段 | 严重违规 | 🔴 |
| 在非编码阶段产出代码 | 严重违规 | 🔴 |
| 阶段完成但未产出文档 | 严重违规 | 🔴 |
| 流程下一步应自动执行却询问用户 | 流程违规 | 🟡 |
| 未声明当前流程状态 | 需修正 | 🟡 |

## 二、行为准则

### 2.1 红线

新功能、架构、核心修改、第三方集成、安全相关必须先确认。

流程：说明理解 → 提供≥2方案 → 分析优缺风险 → 等待选择

### 2.2 核心总则

结果导向、主动补位、质疑优先、最小改动、风险前置、严守边界、大白话优先、共创搭档、技能调用、自成长

### 2.3 代码生成原则

1.第一性原理 2.YAGNI 3.KISS 4.SOLID 5.DRY

场景优先级：
- 新项目：第一性→YAGNI→KISS→SOLID→DRY
- 新功能：YAGNI→KISS→SOLID→DRY→第一性
- 小工具：KISS→DRY→YAGNI→SOLID→第一性
- 复杂组件：第一性→SOLID→YAGNI→KISS→DRY

### 2.4 全流程纪律

| 环节 | 要求 |
|------|------|
| 任务接收 | 复述目标、澄清模糊点 |
| 问题分析 | 读全错误/代码，列根因及位置、证据 |
| 方案设计 | 明确修改位置/思路，必须同时说明优点、弊端、风险 |
| 代码修改 | 仅改强相关代码，说明每处修改原因 |
| 沟通话术 | 推测性修改必声明，禁绝对化承诺 |
| 介入触发 | 错误模糊、需改核心、无把握时必暂停 |
| 交付要求 | 提交修改总结，披露风险 |

### 2.5 流程铁律

**以下规则优先级最高，任何情况下不可违反：**

1. **流程先于行动** — 收到任何任务，先判断当前处于哪个流程阶段，再决定做什么
2. **只做当前阶段的事** — 需求阶段只产出需求文档，设计阶段只产出技术方案，编码阶段才写代码
3. **文档是阶段完成的唯一凭证** — 没有产出文档 = 阶段未完成 = 不能进入下一阶段
4. **下一步自动执行** — 当前阶段完成后，直接进入下一阶段并调用对应技能，不需要询问用户
5. **跳步即违规** — 任何跳步行为，无论理由多充分，都是违规

### 2.6 底线

不草率乱改、不假装懂、不炫技、不甩锅、严守红线、绝不跳步

## 三、代码规范

**所有源代码文件必须包含注释，无注释的代码视为不完整。**

> 具体注释格式（文件头、函数、行内）按项目技术栈配置，详见 `specs/project_config.md`。

### 3.1 文件头注释（强制）

每个源代码文件必须在顶部添加文件头注释，说明文件用途。

规则：
- 新建文件时必须同时添加文件头注释
- 文件头注释必须在文件第一行（import 语句之前）
- 描述用中文，简洁准确，一句话说清"这个文件是干嘛的"
- 豁免文件类型：`*.d.ts`（纯类型声明）、`*.css`、`*.json`、自动生成的文件

### 3.2 函数/组件注释（推荐）

必须添加的场景：
- 导出的函数/组件（export）
- 业务逻辑复杂的函数
- 工具函数（utils/、hooks/）

### 3.3 行内注释（按需）

规则：
- 注释解释"为什么"，而不是"做了什么"（代码本身应说明做了什么）
- 临时方案、兼容处理、特殊边界情况必须加注释

### 3.4 违规判定

| 场景 | 判定 |
|------|------|
| 新建文件无文件头注释 | 严重违规 |
| 修改文件后文件头注释与实际用途不符 | 需修正 |
| 导出函数/组件无注释 | 建议补充 |
| 复杂业务逻辑无行内注释 | 建议补充 |

## 四、版本管理

### 4.1 语义化版本规则

遵循语义化版本（SemVer）：`major.minor.patch`

| 版本位 | 递增条件 | 示例 |
|--------|---------|------|
| major | 不兼容的架构变更、数据库大版本迁移 | 1.0.0 → 2.0.0 |
| minor | 新功能、数据库新增表/字段 | 1.0.0 → 1.1.0 |
| patch | BUG修复、UI微调、配置变更 | 1.0.0 → 1.0.1 |

### 4.2 版本文档同步规则

**每次代码变更完成后，必须同步更新对应的版本文档。**

1. **文档位置**：`specs/releases/v{版本号}.md`（多端项目在 `project_config.md` 中配置各端路径）
2. **同步时机** - 每次完成功能开发、BUG修复、配置变更后，必须立即更新对应版本的 release 文档
3. **更新内容** - 包括但不限于：修改文件清单、变更描述、新增功能说明、BUG修复说明、迁移风险、数据库变更
4. **新建版本** - 当进入新版本开发时，必须先创建对应的 `specs/releases/v{新版本号}.md`
5. **发布记录** - 版本发布时必须在版本文档的基本信息表中记录「实际发布时间」（精确到分钟），格式如 `2026-05-17 23:50`
6. **违规判定** - 代码变更完成但未同步更新版本文档视为流程违规

### 4.3 发版确认规则

**版本发布必须由用户明确确认后才能执行。**

1. **禁止自动发版** - 任何版本发布（构建安装包、创建Release、推送标签等）必须等待用户明确确认
2. **确认方式** - 用户必须明确说出"发版"、"发布"、"可以发版"等确认性语言，或用户在对话中明确指示直接发版
3. **例外** - 仅当用户在对话中明确说"你直接发版"、"不用确认直接发"等授权性语言时，才可跳过确认
4. **违规判定** - 未经用户确认擅自执行发版操作视为严重违规

### 4.4 数据库变更与版本号

- 涉及数据库变更（新增表/字段/迁移） → 至少 minor 版本递增
- 不涉及数据库变更 → patch 版本递增
- 需求澄清阶段必须标注是否涉及数据库变更
- 数据库变更必须保证多端兼容（如适用）

## 五、质量门禁

### 5.1 编码完成后

- 必须运行 lint 和 typecheck（如项目配置了相关命令）
- 必须更新版本文档（如当前有活跃版本）

### 5.2 功能完成后

- 必须通过功能验收
- 必须更新项目进度
- 必须同步版本文档

### 5.3 发布前

- 编译检查必须通过（tsc / cargo check 等）
- 版本号在所有配置文件中必须一致（具体文件清单见 `project_config.md`）
- changelog 必须包含新版本条目（如适用）

## 六、技能匹配协议

**执行任务前必须：**

### 6.1 动态扫描规则

执行任务前，扫描 `.trae/skills/` 目录获取当前可用技能列表，根据技能的 `description` 字段匹配当前任务。

### 6.2 匹配检查流程

1. **技能匹配检查** - 扫描可用技能，检查是否匹配
2. **用户指定技能验证** - 检查适用性，不适用需说明原因并建议替代，等待确认
3. **强制调用匹配技能** - 有匹配必须立即调用 Skill 工具

### 6.3 违规判定

未检查技能、用户指定不适用未说明、有匹配未调用、调用错误

### 6.4 初始化命令

`init`/`协议初始化`/`初始化`/`project-protocol-init` 时立即调用 `project-protocol-init`，并读取三个协议文件
