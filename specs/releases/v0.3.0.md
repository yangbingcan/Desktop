## 二、变更摘要

### 2.1 修复（Bug Fixes）

| 编号 | 描述 | 影响 |
|------|------|------|
| AC-P-02 | 采购入库单无法查询历史记录 | 阻塞数据闭环 |
| AC-P-03 | 采购入库单无法按供应商筛选 | 阻塞供应商对账 |
| BUG-PO-01 | `purchase_in` 中 `purchase_items` 在 `purchase_orders` 之前插入，违反外键约束 | 数据库操作直接失败 |
| BUG-PO-02 | 单号 `order_no` 只用毫秒（0-999），同毫秒多次入库会触发 UNIQUE 约束 | 高频入库场景下数据丢失 |
| BUG-PO-03 | `get_purchase_orders` SQL 列顺序与 `row.get(N)` 索引不一致（item_count/remark/created_at 错位） | 列表数据错位（付款状态显示到金额字段等） |

### 2.2 新增（Features）

| 编号 | 描述 |
|------|------|
| M04-PO-01 | 采购入库单正确持久化主单和明细（v0.2.0 时期主单未保存） |
| M04-PO-02 | 采购入库单列表 API + 前端 UI（支持日期/供应商/付款状态筛选） |
| M04-PO-03 | 采购入库单详情页 `/purchase/:id` |
| M04-PO-04 | PurchaseInput 增 paymentStatus 字段 |

### 2.3 数据库变更

- ⚠️ **新增表 `purchase_orders`**（采购主单）：id / order_no / supplier_id / handler / total_amount / payment_status / remark / created_at
- ⚠️ **新增表 `purchase_items`**（采购明细）：id / order_id / product_id / unit_id / quantity / grams / unit_price / subtotal / batch_id / ...
- 新增 6 个索引（4 个主单 + 1 个明细 + 1 个外键）
- SCHEMA_VERSION 升级：2 → 3

## 三、迁移指南

### 3.1 自动迁移

v0.3.0 启动时自动执行 `migrate_v3_purchase_orders` 迁移：

1. 创建 `purchase_orders` 表（含 4 个索引）
2. 创建 `purchase_items` 表（含 1 个索引）
3. 设置 `user_version = 3`

**重要**：v0.2.0 时期的采购入库数据**不会自动回填**到 `purchase_orders` 表，原因是缺乏完整的主单信息（handler、payment_status、remark）。

### 3.2 数据兼容性

- ✅ v0.2.0 用户的现有数据（products / inventory_batches / stock_flow / sales_* / members / suppliers / return_*）完全保留
- ✅ 前端 API 兼容：`purchase_in` 入参新增 `paymentStatus` 可选字段（默认为 'unpaid'）
- ✅ 老数据（v0.2.0 时期的批次/流水）可继续使用，不受影响

### 3.3 升级前备份（建议）

```powershell
# 复制 .db 文件到备份目录
copy %APPDATA%\tea-manage\tea.db %APPDATA%\tea-manage\tea.db.bak.v0.2.0
```

## 五点五、单元测试清单

> 通过 5 个单元测试验证核心逻辑（使用 in-memory SQLite，避免污染真实数据）

| # | 测试 | 覆盖场景 | 状态 |
|---|------|---------|------|
| 1 | `test_purchase_in_success` | 成功路径：主单/明细/批次/库存/流水全部写入 | ✅ |
| 2 | `test_purchase_in_rollback_on_invalid_supplier` | 无效供应商回滚（不存在/已停用） | ✅ |
| 3 | `test_query_purchase_orders_filter_by_supplier` | 按供应商 + 付款状态筛选 | ✅ |
| 4 | `test_query_purchase_orders_date_range` | 日期范围筛选（含当天） | ✅ |
| 5 | `test_query_purchase_order_detail` | 详情查询（含明细）+ 不存在 ID 报错 | ✅ |

**测试中发现的 3 个生产 Bug（已修复）**：

1. **BUG-PO-01 外键约束**：`purchase_items` 在 `purchase_orders` 之前插入，违反 `order_id` 外键
   - 修复：先插入主单，再循环插入明细
2. **BUG-PO-02 单号冲突**：`order_no` 只用毫秒（0-999），同毫秒多次入库会触发 UNIQUE 约束
   - 修复：单号改为 `RK + 时间戳(秒) + 毫秒(3位) + 随机后缀(4位)`
3. **BUG-PO-03 列序错位**：`get_purchase_orders` 的 SQL 列顺序与 `row.get(N)` 不一致
   - 修复：调整 SQL `SELECT` 列顺序为 `id, order_no, supplier_id, supplier_name, handler, total_amount, payment_status, item_count, remark, created_at`

## 六、关键技术决策

### 6.1 重构 vs 新增 Command

| 方案 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| A：重构 `purchase_in` | 单点维护，API 兼容 | 函数变长 | ✅ |
| B：新增 `create_purchase_order` | 职责清晰 | 老 API 仍存在不完整数据风险 | ❌ |

### 6.2 v0.2.0 历史数据策略

| 方案 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| A：回填到 purchase_orders | 数据完整 | 缺字段会出错 | ❌ |
| B：不回填 | 数据准确 | 旧批次无主单 | ✅ |

### 6.3 付款状态字段

`TEXT + CHECK 约束`，允许值：`unpaid` / `partial` / `paid`

## 七、风险与回滚

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| `purchase_in` 函数变长 | 高 | 中 | 函数内部分段（步骤 1-6），加注释 |
| 单元测试中 Tauri State 注入复杂 | 中 | 低 | 后续 D1 任务组用集成测试 |
| v0.2.0 用户数据无主单 | 低 | 低 | 文档说明；老批次可继续使用 |
| 详情页加载慢 | 低 | 低 | 索引已建，单条查询 < 10ms |

**回滚方案**（如需回滚到 v0.2.0）：

1. 卸载 v0.3.0 应用
2. 安装 v0.2.0 安装包
3. 数据库自动从 v3 回滚到 v2（需手动执行迁移脚本）
4. v0.3.0 新增的采购单数据**保留**（不删除），但前端不会显示
