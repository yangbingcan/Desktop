## 二、背景与价值

### 2.1 业务背景

v0.1.0 时期 `purchase_in` Command 实现了库存扣减逻辑，但**没有将采购单据本身保存到数据库**。这导致：

- 无法查询历史采购记录
- 无法按供应商统计进货量
- 无法按日期范围追溯采购成本
- 退货出库时无法关联原采购单据
- 财务对账无据可查

### 2.2 目标用户

- **店长**：盘点采购成本、查看供应商交易历史
- **采购员**：跟踪进货明细
- **财务**：月度/季度对账（未来）

### 2.3 使用场景

| 场景 | 描述 |
|------|------|
| 月末盘点 | 店长打开「采购入库单」列表，筛选本月记录，导出对账 |
| 供应商对账 | 选择某供应商，查看该供应商所有历史采购单 |
| 价格追溯 | 客户询问某批次茶叶的进货价，店员通过批次号反查采购单 |
| 退货时关联 | 创建退货单时（如未来扩展），可关联原始采购单据 |

### 2.4 业务价值

- **数据闭环**：所有库存变动都有完整单据可追溯
- **决策支持**：基于历史采购数据优化采购策略
- **合规要求**：财务审计需要可追溯的采购凭证
- **风险降低**：避免「只有库存变动、没有单据记录」的黑箱

## 四、验收标准

### AC-01：创建采购入库单时同时持久化主单和明细

- **Given**: 数据库 schema 版本为 2（v0.2.0 状态）
- **When**: 用户通过前端创建一笔新的采购入库单（带 1 个及以上商品明细）
- **Then**:
  - `purchase_orders` 表新增 1 条主单记录（含 `id` / `order_no` / `supplier_id` / `handler` / `total_amount` / `remark` / `payment_status` / `created_at`）
  - `purchase_items` 表新增 N 条明细记录（每条对应一个商品行）
  - `inventory_batches` 表新增 N 条批次记录
  - `products` 表库存增加正确
  - `stock_flow` 表新增 N 条流水记录
  - 整个过程在单一数据库事务中，任意一步失败则全部回滚

### AC-02：采购入库单能按日期范围筛选

- **Given**: 数据库存在 5 条不同日期的采购单（分散在 3 个月）
- **When**: 用户在前端列表中设置日期范围（如 2026-05-01 至 2026-05-31）
- **Then**:
  - 列表仅显示该日期范围内的采购单
  - 表格总数（total）等于该范围内的记录数
  - 日期边界包含（>= 起始日期 且 <= 截止日期）

### AC-03：采购入库单能按供应商筛选

- **Given**: 数据库存在 3 个供应商的采购单
- **When**: 用户在前端列表中选择某个供应商
- **Then**:
  - 列表仅显示该供应商的采购单
  - 表格显示的供应商名称正确

### AC-04：采购入库单列表显示供应商名称

- **Given**: 数据库存在采购单数据
- **When**: 用户打开「采购入库单」列表
- **Then**:
  - 列表表格中包含「供应商」列
  - 显示的是供应商名称（通过 `supplier_id` 关联 `suppliers.name`）而非 ID

### AC-05：采购入库单列表显示付款状态

- **Given**: 数据库存在不同付款状态的采购单
- **When**: 用户打开列表
- **Then**:
  - 列表显示「付款状态」列（未付款/部分付款/已付款）
  - 不同状态有不同颜色标签（可选）

### AC-06：采购入库单详情页可访问

- **Given**: 数据库存在某条采购单
- **When**: 用户在列表中点击该条记录的「详情」按钮
- **Then**:
  - 跳转到采购单详情页（`/purchase/:id`）
  - 详情页显示完整的单据信息（单号、日期、供应商、经手人、付款状态、备注）
  - 详情页显示商品明细表（商品名、单位、数量、克数、单价、小计、批次号）
  - 详情页显示总金额
  - 详情页提供「返回列表」按钮

### AC-07：采购入库单分页正常

- **Given**: 数据库存在超过 20 条采购单
- **When**: 用户在列表中翻到第 2 页
- **Then**:
  - 正确显示第 2 页的 20 条数据
  - 分页器显示正确的总条数
  - URL 或状态保留当前页码（刷新后保持）

### AC-08：数据库 schema 升级到 v3

- **Given**: v0.2.0 用户首次启动 v0.3.0 应用
- **When**: 应用启动时执行数据库迁移
- **Then**:
  - 自动检测当前 `user_version` < 3
  - 执行 `migrate_v3_purchase_orders` 创建 `purchase_orders` 和 `purchase_items` 表
  - 幂等执行（重复执行不会报错）
  - 完成后 `user_version` 更新为 3
  - 现有数据保留（不破坏 `purchase_orders.supplier_id` 已迁移到 'sup-default' 的记录）

### AC-09：单元测试覆盖核心逻辑

- **Given**: 后端 Commands 已实现
- **When**: 运行 `cargo test`
- **Then**:
  - `create_purchase_order` 测试通过：含事务回滚场景
  - `get_purchase_orders` 测试通过：含日期/供应商/分页筛选
  - `get_purchase_order_detail` 测试通过：含明细聚合

## 五、功能流程

### 5.1 正常流程（创建采购单 + 列表查询）

```
1. 用户在 PurchaseForm.vue 填写表单
   ↓
2. 点击「保存」
   ↓
3. 前端调用 invoke('purchase_in', { input })
   ↓
4. 后端 BEGIN EXCLUSIVE TRANSACTION
   ├── 4.1 校验供应商存在
   ├── 4.2 遍历明细：
   │      ├── 计算克数（quantity × conversion）
   │      ├── 生成批次号（RK + 日期 + UUID 8位）
   │      ├── INSERT inventory_batches
   │      ├── UPDATE products.stock_grams
   │      └── INSERT stock_flow
   ├── 4.3 INSERT purchase_orders 主单
   └── 4.4 INSERT purchase_items 明细
   ↓
5. COMMIT
   ↓
6. 前端跳转到详情页
   ↓
7. 详情页调用 get_purchase_order_detail
   ↓
8. 详情页显示完整单据信息
```

### 5.2 列表查询流程

```
1. 用户打开 /purchase
   ↓
2. PurchaseList.vue onMounted
   ↓
3. 调用 get_purchase_orders(page, pageSize, supplierId?, dateStart?, dateEnd?, paymentStatus?)
   ↓
4. 后端构建动态 SQL
   ↓
5. 返回分页结果
   ↓
6. 列表渲染
```

### 5.3 异常流程

| 异常 | 处理方式 |
|------|----------|
| 供应商已停用 | 后端 `purchase_in` 校验 `is_active=1`，不通过则回滚事务 |
| 商品不存在 | 后端事务回滚，返回错误信息 |
| 批次生成冲突 | 后端使用 UUID 8 位避免冲突 |
| 数据库迁移失败 | 应用启动时打印错误日志，提示用户备份数据 |
| 详情页 ID 不存在 | 详情页显示「采购单不存在」空状态 |

## 六、数据需求

### 6.1 新增数据库表

#### 6.1.1 `purchase_orders` 表（v0.3.0 新建）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | TEXT | PRIMARY KEY | UUID |
| order_no | TEXT | UNIQUE NOT NULL | 采购单号（RK+日期+序号+毫秒） |
| supplier_id | TEXT | NOT NULL | 供应商 ID（FK） |
| handler | TEXT | NULL | 经手人 |
| total_amount | REAL | NOT NULL DEFAULT 0 | 总金额 |
| payment_status | TEXT | NOT NULL DEFAULT 'unpaid' | 付款状态：unpaid / partial / paid |
| remark | TEXT | NULL | 备注 |
| created_at | TEXT | NOT NULL | 创建时间 |

**索引**：
- `idx_purchase_order_no` (order_no)
- `idx_purchase_supplier` (supplier_id)
- `idx_purchase_date` (created_at)
- `idx_purchase_payment_status` (payment_status)

**外键**：
- `supplier_id` REFERENCES `suppliers(id)` ON DELETE RESTRICT

#### 6.1.2 `purchase_items` 表（v0.3.0 新建）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| id | TEXT | PRIMARY KEY | UUID |
| order_id | TEXT | NOT NULL | 采购单 ID（FK） |
| product_id | TEXT | NOT NULL | 商品 ID（FK） |
| product_name | TEXT | NOT NULL | 商品名称（冗余） |
| unit_id | TEXT | NOT NULL | 销售单位 ID（FK） |
| unit_name | TEXT | NOT NULL | 单位名称（冗余） |
| quantity | INTEGER | NOT NULL | 数量 |
| grams | INTEGER | NOT NULL | 克数（换算后） |
| unit_price | REAL | NOT NULL | 进价 |
| subtotal | REAL | NOT NULL | 小计金额 |
| batch_id | TEXT | NOT NULL | 批次 ID（FK） |
| batch_code | TEXT | NOT NULL | 批次号（冗余） |
| created_at | TEXT | NOT NULL | 创建时间 |

**索引**：
- `idx_purchase_item_order` (order_id)

**外键**：
- `order_id` REFERENCES `purchase_orders(id)` ON DELETE CASCADE
- `product_id` REFERENCES `products(id)` ON DELETE RESTRICT
- `unit_id` REFERENCES `sales_units(id)` ON DELETE RESTRICT
- `batch_id` REFERENCES `inventory_batches(id)` ON DELETE RESTRICT

## 八、依赖与约束

### 8.1 依赖

- M01-商品档案：商品/单位/换算关系
- M02-库存管理：批次/流水
- M04 供应商档案：suppliers 表（v0.2.0 已建）
- @tauri-apps/api 1.x

### 8.2 约束

- `purchase_in` 必须在单一事务中完成所有操作
- `purchase_orders.order_no` 必须全局唯一（使用 UUID 8 位 + 时间戳）
- `purchase_items.batch_id` 必须关联已存在的批次

### 8.3 版本控制影响

- **数据库变更**：⚠️ **涉及**（新增 2 张表）
- **建议版本号**：v0.2.0 → **v0.3.0**（minor 递增）
- **SCHEMA_VERSION**：2 → **3**
- **迁移需求**：✅ 需要
- **迁移逻辑**：`migrate_v3_purchase_orders`（幂等）

### 8.4 数据迁移策略

**v0.2.0 → v0.3.0 迁移步骤**：

```sql
-- 1. 创建 purchase_orders 表
CREATE TABLE IF NOT EXISTS purchase_orders (...);
CREATE INDEX IF NOT EXISTS idx_purchase_order_no ON purchase_orders(order_no);
-- ... 其他索引

-- 2. 创建 purchase_items 表
CREATE TABLE IF NOT EXISTS purchase_items (...);
CREATE INDEX IF NOT EXISTS idx_purchase_item_order ON purchase_items(order_id);

-- 3. user_version 升级
PRAGMA user_version = 3;
```

**注意**：v0.2.0 之前的采购入库记录（仅有 `inventory_batches` / `stock_flow`）**不回填**到 `purchase_orders`，因为没有完整的主单信息。这是有意为之 — 避免数据错误。

## 十、风险与决策

| 风险 | 决策 | 理由 |
|------|------|------|
| 已有采购数据无法回填 | 不回填，从 v0.3.0 开始记录主单 | 避免数据错误和误判 |
| `purchase_in` 函数变得复杂 | 拆分为 `insert_purchase_header` + `insert_purchase_items` + `update_stock_and_batches` | 单一职责，便于测试 |
| 批次号生成冲突 | 使用 `RK + yyyymmdd + UUID 8位` 组合 | UUID 几乎不可能重复 |
| 付款状态字段 | 从 v0.3.0 开始强制记录 | 老数据用 'unpaid' 默认 |
